# 幻想世界国家角色扮演游戏辅助平台

## 软件需求说明书

**文档版本：** V1.0
**产品形态：** 网页应用
**目标用户：** 小规模熟人玩家群体
**建议规模：** 1 名主持人，3 至 8 名玩家
**核心模式：** 主持人驱动的异步回合制国家角色扮演游戏

---

# 1. 项目概述

## 1.1 项目背景

本项目来源于一种线下多人回合制角色扮演游戏。

游戏发生在主持人设计的幻想或架空世界中。玩家通常扮演一国之主、领主、军阀或组织首领，负责管理所属势力，并通过提交“政策”实施探索、军事、外交、建设及角色行动。

每个回合中，主持人公布当前世界状态、可执行行动和临时规则。玩家根据自己的目标提交政策。主持人收集所有政策后，结合规则、世界设定和其他玩家的行动进行统一裁定，并向玩家反馈结果。

反馈通常同时包含：

1. 政策是否成功。
2. 资源和状态变化。
3. 地图和势力变化。
4. 触发的事件。
5. 公共或私密情报。
6. 故事性叙述。

线下游戏依赖纸质政策、面对面讨论和主持人人工记录。玩家无法长期线下聚集后，需要通过网页平台支持远程、异步和持续游玩。

## 1.2 产品定位

本产品定位为：

**面向小规模熟人组局的主持人驱动型国家角色扮演游戏辅助平台。**

产品可参考《文明6》和《红色警戒》的地图与战略信息呈现方式，同时保留桌面角色扮演游戏中的自由行动、角色扮演和主持人裁量。

平台主要辅助游戏流程，不承担完全自动裁定职责。

## 1.3 产品目标

系统需要实现以下目标：

1. 集中展示世界、地图、国家和角色信息。
2. 支持玩家远程填写和提交政策。
3. 帮助主持人统一审核和结算政策。
4. 分别发布公共结果和私人结果。
5. 保存每个回合的政策、事件和世界变化。
6. 降低主持人整理信息和撰写反馈的工作量。
7. 支持不同题材和不同规则的游戏剧本。
8. 保留主持人对规则和故事发展的最终决定权。

## 1.4 产品边界

首版产品主要提供游戏管理和结算辅助能力。

首版不追求实现完整的即时战略游戏、复杂战争模拟或自动主持人。

《文明6》和《红色警戒》仅作为界面和信息呈现参考，不作为首版功能范围标准。

# 2. 用户角色

## 2.1 主持人

主持人负责创建游戏、维护世界状态、管理回合、审核政策和发布结果。

主持人可以：

1. 创建游戏房间。
2. 邀请玩家。
3. 分配国家和主要角色。
4. 编辑世界背景、地图和规则。
5. 设置每回合政策额度。
6. 查看所有玩家政策。
7. 要求玩家补充政策。
8. 对政策进行人工裁定。
9. 修改资源、角色、地图和势力状态。
10. 发布公共和私人结果。
11. 创建事件和战斗。
12. 修正已经发布的错误结果。

主持人对游戏结果拥有最终裁定权。

## 2.2 玩家

玩家负责扮演指定国家和主要角色。

玩家可以：

1. 查看有权获知的世界信息。
2. 查看所属国家、角色和资源状态。
3. 查看地图和已知区域。
4. 填写和提交政策。
5. 回复主持人的补充请求。
6. 处理事件和外交提案。
7. 查看自己的政策结果。
8. 查看公共世界纪事。
9. 查看历史回合和私人情报。

## 2.3 旁观者

旁观者只能查看主持人公开的信息。

旁观者不能：

1. 提交政策。
2. 查看玩家秘密政策。
3. 查看私人事件。
4. 修改游戏状态。

# 3. 核心游戏对象

## 3.1 游戏房间

游戏房间代表一场独立进行的游戏。

每个房间包含：

1. 主持人和玩家。
2. 世界背景。
3. 当前回合。
4. 地图。
5. 国家和角色。
6. 游戏规则。
7. 历史记录。

## 3.2 国家或势力

国家是玩家主要管理的战略对象。

国家可以包含：

1. 名称和旗帜。
2. 领土。
3. 资源。
4. 自定义属性。
5. 军队。
6. 角色。
7. 外交关系。
8. 持续状态。

国家属性由剧本决定。

系统可提供人口、稳定度、威望和科技等常用模板，但不要求所有剧本使用。

## 3.3 角色

角色承担角色扮演和故事推进功能。

角色可以包含：

1. 姓名和头像。
2. 身份和所属势力。
3. 公开背景。
4. 私密背景。
5. 属性和特质。
6. 健康状态。
7. 所在区域。
8. 人物关系。
9. 个人目标。

每名玩家原则上拥有一名主要扮演角色，同时可以管理若干下属角色。

## 3.4 地图区域

首版使用区域式地图。

每个区域可以包含：

1. 区域名称。
2. 地形。
3. 控制势力。
4. 已知资源。
5. 驻军。
6. 建筑。
7. 事件。
8. 探索状态。
9. 与其他区域的连接关系。

系统需要支持战争迷雾。玩家只能获取自己已经发现或有权获知的区域信息。

## 3.5 政策

政策是玩家每回合执行行动的基本单位。

政策类型可以包括：

1. 探索政策。
2. 军事政策。
3. 外交政策。
4. 内政政策。
5. 建设政策。
6. 角色行动。
7. 自由政策。

主持人可以为每回合设置不同的政策额度。

## 3.6 事件

事件用于表达剧情发展、探索发现、外交请求、自然灾害和角色冲突。

事件可以：

1. 直接产生结果。
2. 要求玩家选择。
3. 要求玩家自由回复。
4. 仅对指定玩家可见。
5. 延续为后续事件。

## 3.7 战斗

战斗是特殊的政策结算。

首版支持：

1. 野战。
2. 攻城战。
3. 主持人自定义战斗。

战斗结果由兵力、修正值、骰子和主持人裁定共同决定。

# 4. 核心回合流程

## 4.1 回合状态

首版采用以下六个主要状态：

| 状态     | 说明                                 |
| -------- | ------------------------------------ |
| 回合准备 | 主持人设置公告、额度、事件和截止时间 |
| 政策收集 | 玩家查看信息并提交政策               |
| 政策审核 | 主持人检查政策并要求必要补充         |
| 政策结算 | 主持人处理政策、事件和战斗           |
| 结果预览 | 主持人检查状态变化和玩家可见内容     |
| 回合完成 | 系统发布结果并归档回合               |

附加状态包括：

1. 已暂停。
2. 已取消。

## 4.2 回合准备

主持人需要设置：

1. 回合编号。
2. 世界时间。
3. 回合公告。
4. 本回合公共事件。
5. 各类政策额度。
6. 政策提交截止时间。
7. 临时规则。
8. 玩家私人情报。

主持人确认后开放回合。

## 4.3 政策收集

玩家可以：

1. 查看回合公告。
2. 查看地图和国家状态。
3. 创建政策草稿。
4. 修改政策草稿。
5. 提交政策。
6. 查看剩余政策额度。
7. 确认本回合提交完成。

在主持人锁定回合前，玩家可以撤回或修改政策。

## 4.4 政策审核

主持人集中查看所有政策。

审核内容包括：

1. 政策描述是否完整。
2. 政策目标是否明确。
3. 资源是否足够。
4. 角色或军队是否可用。
5. 是否违反当前规则。
6. 是否与其他政策冲突。
7. 是否需要玩家补充说明。

个别政策需要补充时，回合仍保持在政策审核阶段。

## 4.5 政策结算

主持人按适当顺序处理政策。

每项政策可以产生：

1. 成功、部分成功、失败或无效。
2. 资源消耗或获得。
3. 国家属性变化。
4. 角色状态变化。
5. 地图变化。
6. 军队变化。
7. 外交关系变化。
8. 新事件。
9. 公共反馈。
10. 私人反馈。

结算结果在正式发布前只作为草稿保存。

## 4.6 结果预览

主持人需要检查：

1. 每项政策是否已完成结算。
2. 是否存在资源负数等非法状态。
3. 是否有未处理事件。
4. 公共结果是否包含秘密信息。
5. 每名玩家是否拥有正确的私人结果。
6. 地图、国家和角色变化是否正确。

主持人可以分别预览：

1. 公共视角。
2. 指定玩家视角。
3. 主持人完整视角。

## 4.7 回合完成

主持人确认发布后，系统执行：

1. 应用所有状态变化。
2. 发布公共回合结果。
3. 发布玩家私人结果。
4. 更新地图和国家状态。
5. 保存政策和事件记录。
6. 生成世界纪事。
7. 归档当前回合。
8. 创建下一回合草稿。

# 5. 政策系统

## 5.1 政策表单

首版政策表单保留以下字段：

1. 政策名称。
2. 政策类型。
3. 行动目标。
4. 行动描述。
5. 投入资源。
6. 参与角色或军队。
7. 保密范围。
8. 补充说明。

复杂条件、备用计划和分支可以写入行动描述。

系统后续可以根据实际需要增加结构化条件编辑器。

## 5.2 政策状态

| 状态     | 说明               |
| -------- | ------------------ |
| 草稿     | 玩家尚未提交       |
| 已提交   | 等待主持人审核     |
| 需要补充 | 主持人要求补充信息 |
| 已确认   | 可以进入结算       |
| 已结算   | 已生成结算草稿     |
| 已发布   | 结果已经正式发布   |
| 已作废   | 已撤回、拒绝或取消 |

## 5.3 政策冲突

系统可以提示以下明显冲突：

1. 同一角色执行多个互斥行动。
2. 同一军队同时前往多个区域。
3. 同一资源被重复投入。
4. 多名玩家同时行动于同一区域。
5. 外交政策和军事政策目标矛盾。

系统提示仅供主持人参考。

首版无需实现复杂的可视化冲突图。

# 6. 主持人结算流程

## 6.1 结算工作台

主持人工作台应在同一页面展示：

1. 玩家政策原文。
2. 相关国家状态。
3. 相关角色。
4. 相关地图区域。
5. 历史事件。
6. 相关规则。
7. 可能冲突的其他政策。
8. 政策结算编辑区域。
9. 状态修改区域。

## 6.2 快速结算模式

主持人应能够通过以下步骤完成普通政策：

1. 阅读政策。
2. 选择结算结果。
3. 填写反馈内容。
4. 修改相关资源或状态。
5. 保存结算。

系统不应强迫主持人为每项政策建立复杂依赖图或结算组。

## 6.3 高级结算

复杂情况下，主持人可以：

1. 将多项政策联合结算。
2. 设置政策执行顺序。
3. 进行骰子检定。
4. 创建战斗。
5. 创建后续事件。
6. 向不同玩家发布不同结果。

## 6.4 结果内容

每项结算可以包含多段内容，并分别设置可见对象：

1. 所有人可见。
2. 提交玩家可见。
3. 指定玩家可见。
4. 指定阵营可见。
5. 仅主持人可见。

# 7. 简化战斗系统

## 7.1 战斗数据

一次战斗至少记录：

1. 战斗名称。
2. 战斗地点。
3. 战斗类型。
4. 参战方。
5. 双方兵力。
6. 主持人设置的修正值。
7. 骰子结果。
8. 最终结果。
9. 双方损失。
10. 地图变化。
11. 战斗叙事。

## 7.2 战斗结算

首版可采用以下简化模型：

```text
战斗得分
＝
兵力基础值
＋ 战斗类型修正
＋ 地形或城防修正
＋ 角色修正
＋ 骰子结果
＋ 主持人修正
```

主持人可以修改系统建议的结果。

系统不得自动决定最终胜负。

# 8. 页面需求

首版保留四个主要页面。

## 8.1 游戏总览

游戏总览是玩家进入游戏后的主要页面。

页面包含：

1. 世界地图。
2. 当前回合信息。
3. 国家资源摘要。
4. 主要角色摘要。
5. 当前事件。
6. 玩家待办事项。
7. 最新通知。

点击地图区域、角色或军队后，在侧边栏显示详细信息。

## 8.2 政策中心

政策中心包含：

1. 本回合政策额度。
2. 政策草稿。
3. 已提交政策。
4. 主持人补充请求。
5. 已发布政策结果。
6. 提交完成确认。

## 8.3 主持人工作台

主持人工作台通过标签页组织：

1. 回合管理。
2. 玩家提交情况。
3. 政策审核。
4. 政策结算。
5. 事件和战斗。
6. 结果预览。
7. 结果发布。

主持人应尽量在该页面完成一回合的主要操作。

## 8.4 档案与规则

该页面包含：

1. 世界纪事。
2. 历史回合。
3. 国家档案。
4. 角色档案。
5. 战斗记录。
6. 游戏规则书。

# 9. 信息可见性

## 9.1 内容等级

首版支持以下可见范围：

1. 全部玩家可见。
2. 指定玩家可见。
3. 指定国家或阵营可见。
4. 仅主持人可见。

## 9.2 权限原则

1. 权限必须由服务端校验。
2. 客户端不得接收玩家无权查看的真实数据。
3. 玩家不能查看其他玩家的秘密政策。
4. 玩家不能查看未发现区域的真实信息。
5. 主持人发布结果前应能够预览玩家视角。
6. 已发布秘密内容可以由主持人在后续回合公开。

# 10. AI 辅助功能

## 10.1 AI 定位

AI 用于整理信息和生成文本草稿。

AI 不拥有最终裁定权，不能直接修改正式游戏状态。

## 10.2 首版 AI 功能

### 政策摘要

将玩家提交的长政策整理为：

1. 主要目标。
2. 行动方式。
3. 使用资源。
4. 参与角色。
5. 关键条件。
6. 需要主持人确认的问题。

### 对象提取

识别政策涉及的：

1. 国家。
2. 角色。
3. 区域。
4. 军队。
5. 资源。
6. 历史事件。

### 规则与历史检索

帮助主持人查找：

1. 相关规则条文。
2. 角色过去经历。
3. 相关地区事件。
4. 以前类似政策。
5. 已经建立的世界设定。

### 叙事草稿

主持人完成裁定后，AI 根据明确结果生成：

1. 政策反馈草稿。
2. 公共回合总结。
3. 私人情报文本。
4. 简单战报。
5. 世界纪事草稿。

## 10.3 AI 使用限制

1. 所有 AI 输出必须经过主持人确认。
2. AI 不得直接发布结果。
3. AI 不得直接扣除资源或修改地图。
4. 玩家提交的文本视为不可信输入。
5. AI 不得因政策文本中的指令泄露隐藏设定。
6. AI 检索内容必须经过权限过滤。
7. 玩家侧 AI 功能首版默认关闭。
8. AI 服务不可用时，游戏核心流程仍须正常运行。

## 10.4 暂缓功能

首版暂不实现：

1. AI 自动决定政策成功率。
2. AI 自动生成战斗胜负。
3. AI 自动修改游戏状态。
4. AI 自动发布结果。
5. AI 独立充当主持人。
6. 玩家自由询问完整世界设定。

# 11. 非功能需求

## 11.1 数据可靠性

1. 政策草稿自动保存。
2. 已提交政策不能意外丢失。
3. 回合发布操作必须具有完整性保证。
4. 关键修改需要保存历史记录。
5. 已发布内容不能直接覆盖。
6. 错误结果通过修订方式修改。

## 11.2 性能

1. 普通页面应在合理网络环境下快速加载。
2. 地图缩放和拖动应保持流畅。
3. 政策保存操作应及时反馈。
4. 主持人能够处理单回合约 50 项政策。
5. 历史回合增加后，常用页面不应明显变慢。

## 11.3 兼容性

1. 首版优先支持桌面浏览器。
2. 移动端支持查看通知、政策和结果。
3. 主持人工作台优先适配桌面端。
4. 地图和长文本编辑在平板端可以基本使用。

## 11.4 可扩展性

1. 国家属性可以由剧本配置。
2. 资源类型可以由剧本配置。
3. 政策类型可以由主持人配置。
4. 战斗修正规则可以由主持人调整。
5. 系统不能依赖单一世界观。

# 12. 首版功能范围

## 12.1 首版必须实现

1. 用户登录。
2. 游戏房间创建和邀请。
3. 主持人、玩家和旁观者身份。

# 13. 验收标准

首版系统需要通过一次实际游戏进行验证。

建议测试条件：

1. 一名主持人。
2. 四至六名玩家。
3. 五个以上国家或势力。
4. 十二个以上地图区域。
5. 每名玩家每回合提交三至五项政策。
6. 连续运行至少十个回合。
7. 至少发生一次探索事件。
8. 至少发生一次秘密政策。
9. 至少发生一次多人外交。
10. 至少发生一次野战。
11. 至少发生一次攻城战。
12. 至少进行一次已发布结果修订。

系统验收条件：

1. 玩家能够独立完成政策提交。
2. 锁定后玩家不能修改政策。
3. 主持人能够集中查看所有政策。
4. 主持人能够要求单项政策补充。
5. 主持人能够快速完成普通政策结算。
6. 主持人能够处理战斗和事件。
7. 公共和私人信息能够正确隔离。
8. 状态变化在发布前不会影响正式数据。
9. 玩家能够清楚查看本回合结果。
10. 所有历史政策和结果能够查询。
11. 连续十个回合后数据保持完整。
12. AI 不会直接改变游戏结果。
13. AI 不可用时仍能正常游玩。
14. 主持人无需依赖外部表格完成主要结算流程。

# 14. 待确认事项

以下事项需要通过规则设计或实际试玩进一步确认：

1. 每回合持续数小时还是数天。
2. 政策是否统一截止后集中结算。
3. 是否允许玩家提前查看部分结果。
4. 国家资源和属性需要达到何种复杂度。
5. 玩家是否可以共同控制一个国家。
6. 玩家是否可以中途更换国家或角色。
7. 外交讨论是否继续使用外部聊天工具。
8. 战斗骰子和修正公式。
9. 地图区域是否允许军队同时占领。
10. 游戏结束和胜利条件。
11. 是否需要协作主持人。
12. AI 叙事需要遵循的文风和长度。

# 15. 产品核心判断

本产品最关键的业务闭环为：

```text
主持人发布回合
→ 玩家提交政策
→ 主持人审核政策
→ 主持人完成结算
→ 系统应用世界变化
→ 分别发布公共与私人结果
→ 保存历史并进入下一回合
```

首版开发应优先保证该流程简单、可靠和易于使用。

地图、角色、战争、外交和 AI 均用于辅助这一流程，不应增加不必要的操作负担。
