# 第一章 文档目标

## 1.1 设计目的

本说明书用于将SrilankaOL现有规则、产品设计和系统架构转换为可执行的开发计划。

文档需要明确：

- 首版必须解决的问题；
- MVP必须包含的功能；
- 暂不实现的功能；
- 开发阶段及其依赖关系；
- 每阶段的交付物；
- 每阶段的验收条件；
- 首次可玩版本的定义；
- 首次公开测试版本的定义；
- 功能延期和范围控制原则。

## 1.2 MVP定义

SrilankaOL的MVP不是完整自动化的策略游戏。

MVP应能够支持一场小规模、主持人参与的完整游戏，包括：

1. 创建一场游戏；
2. 配置玩家和国家；
3. 展示六角格地图；
4. 展示国家、地区、城市和军队；
5. 隔离不同玩家的信息；
6. 接收玩家行动；
7. 支持玩家与主持人通信；
8. 由主持人整理和裁决行动；
9. 使用状态变更集修改世界；
10. 发布统一季度结果；
11. 保存历史和审计记录；
12. 在严重错误时回滚季度。

AI、自动战斗和复杂内容生成可以提升效率，但不能成为MVP能够运行的前提。

## 1.3 MVP核心成功标准

MVP成功的标准不是功能数量，而是：

> 主持人可以不依赖Excel和大量外部聊天记录，使用网页完成一场至少包含两个季度的多人测试游戏。

# 第二章 首版产品边界

## 2.1 首版核心用户

首版主要面向：

- 一名主持人；
- 三至八名玩家；
- 一场持续多个季度的私人游戏；
- 桌面浏览器使用场景。

首版不以大规模公开服务器为目标。

## 2.2 首版游戏规模建议

首版测试建议控制在：

- 一张地图；
- 五至十个主要国家；
- 一百至三百个地区；
- 数千个六角格；
- 每个玩家控制一个国家；
- 每季度数项主要行动；
- 少量并发战斗；
- 主持人集中结算。

数据模型不应人为限制未来规模，但界面和性能验收以该范围为基准。

## 2.3 首版依赖主持人的部分

首版允许主持人手工处理：

- 特殊行动规则；
- 复杂政策效果；
- 复杂外交裁决；
- 自定义情报结果；
- 高级事件链；
- 战斗特殊效果；
- 非标准对象；
- 复杂冲突合并。

系统必须提供通用状态编辑和变更集机制，使这些手工裁决能够写入正式世界。

## 2.4 首版不追求的目标

首版不追求：

- 完全自动主持；
- 全自动季度结算；
- 无主持人在线游戏；
- 实时即时战略操作；
- 大规模公开匹配；
- 完整经济模拟；
- 完整国际贸易系统；
- 精细人口阶层模拟；
- 完整宗教传播系统；
- 复杂海战系统；
- 3D地图；
- 高级战斗动画；
- 自治多Agent系统。

# 第三章 功能优先级定义

## 3.1 P0：不可缺少

缺少该功能，核心游戏流程无法运行。

例如：

- 登录；
- 游戏成员；
- 地图查看；
- 行动提交；
- 主持人审核；
- 状态变更；
- 权限隔离；
- 季度发布。

## 3.2 P1：首版重要

缺少该功能仍可勉强运行，但主持人负担、误操作风险或玩家体验明显恶化。

例如：

- 玩家视角预览；
- 消息关联对象；
- 冲突检测；
- 地图编辑；
- 季度回滚；
- 基础Agent辅助。

## 3.3 P2：可延期

可以在MVP之后补充，不阻塞首次完整测试。

例如：

- 自动事件生成；
- 完整战斗模拟器；
- 高级情报网络；
- 复杂任务树；
- 地图动画；
- 批量平衡测试。

## 3.4 P3：远期扩展

当前不进入首版排期。

例如：

- 大规模微服务；
- 模组市场；
- 实时多人战术控制；
- 移动端完整后台；
- 无主持人的AI自治世界。

# 第五章 开发阶段总览

建议将开发划分为九个阶段：

| 阶段 | 名称                 | 主要目标                   |
| ---- | -------------------- | -------------------------- |
| M0   | 产品与工程基线       | 建立项目骨架和需求基线     |

| M7   | 世界管理 Agent       | 自然语言辅助主持人管理世界 |
| M8   | 测试、优化与首版发布 | 完成稳定性和体验验证       |

战斗模拟器可以作为独立支线，在M6之后开始开发。

6. 当前季度能够被创建和读取；
7. 用户刷新页面后仍保持正确游戏身份。

6. 城市必须关联有效地块；
7. 对象详情与地图显示保持一致；
8. 地图接口不会一次返回全部世界历史。

7. 前端源代码或网络请求中不包含被隐藏的真实字段；

## 10.6 验收条件

1. 玩家可以创建并提交完整行动；
2. 主持人可以要求玩家补充；
3. 原始行动不会被主持人版本覆盖；
4. 玩家不能查看其他国家秘密行动；
5. 非会话成员不能读取消息；
6. 玩家能从地图对象页面创建关联行动；
7. 行动截止后系统可以禁止普通修改；
8. 所有状态变化有明确记录。

# 第十一章 M5：状态变更与世界版本

## 11.1 阶段目标

建立正式世界的唯一安全修改通道。

## 11.2 主要功能

- 状态变更集；
- 标准变更操作；
- 变更预览；
- 主持人批准；
- 原子事务；
- 世界版本；
- 对象版本；
- 幂等提交；
- 审计记录；
- 前置条件；
- 基础读写集合；
- 同字段冲突检查；
- 修正变更集。

## 11.3 主持人编辑迁移

M2中的主持人对象编辑必须改为：

> 编辑草稿
> → 状态变更集
> → 预览
> → 批准
> → 正式提交

不得保留绕过变更集的正式编辑接口。

## 11.4 验收条件

1. 所有正式对象修改均产生变更集；
2. Agent、前端和脚本均不能直接修改正式对象；
3. 变更集重复提交不会重复执行；
4. 修改前后差异能够完整展示；
5. 对象版本冲突不会静默覆盖；
6. 同一字段的两个冲突变更能够被识别；
7. 关键操作失败时整个事务回滚；
8. 每次成功提交产生新的世界版本；
9. 审计记录能够追踪修改来源；
10. 已提交结果可以通过修正变更集更正。

# 第十三章 M7：世界管理 Agent

## 13.1 阶段目标

降低主持人处理自定义行动和世界编辑的工作量。

## 13.2 首版Agent能力

实现一个世界管理 Agent，支持：

- 自然语言输入；
- 任务类型识别；
- 对象搜索；
- 对象歧义处理；
- 当前状态查询；
- 相关历史摘要；
- 规则摘要查询；
- 建议处理方案；
- 状态变更集草稿；
- Token和调用记录。

## 13.3 首版工具

首版至少提供：

- `world.search_objects`
- `world.get_object_context`
- `world.get_related_objects`
- `rules.get_applicable_rules`
- `map.calculate_route`
- `changes.create_draft`
- `changes.check_draft`

## 13.4 成本控制

实现：

- 任务复杂度判断；
- 最小上下文；
- Token预算；
- 最大工具调用次数；
- 模型分级；
- 主持人选择简化模式；
- AI不可用时手工降级。

## 13.5 验收示例

主持人输入：

> A国的离间计成功，部分守军打开城门，剩余守军退入内堡。

1. 识别或要求确认目标城市；
2. 查询当前控制者、守军和进攻军队；
3. 提示可能存在的状态矛盾；
4. 生成事件草稿；
5. 生成状态变更草稿；
6. 不直接提交正式世界；
7. 由主持人修改并批准。

## 13.6 验收条件

1. Agent无法调用正式写入接口；
2. 歧义对象不会被自动错误选择；
3. Agent使用的上下文范围可以审计；
4. 输出不符合结构时不会生成正式草稿；
5. 主持人能够完全修改Agent结果；
6. AI不可用时游戏仍能运行；
7. 简单任务不强制调用专项Agent；
8. 每次调用能够统计Token成本。

# 第十九章 需求变更管理

## 19.1 新需求分类

任何新需求先分类为：

- 修复现有核心流程；
- MVP必需；
- 改善体验；
- 自动化提升；
- 玩法扩展；
- 远期设想。

## 19.2 进入当前迭代的条件

新需求只有同时满足以下条件时才能进入当前阶段：

1. 不实现会阻塞该阶段验收；
2. 已有数据模型能够支持；
3. 不会破坏核心权限或版本边界；
4. 复杂度和成本已经评估；
5. 具有明确验收条件。

## 19.3 延后原则

以下需求默认延后：

- 只在极少数情况下使用；
- 可以由主持人手工处理；
- 需要新增大量数据模型；
- 会显著增加界面复杂度；
- 依赖尚未完成的系统；
- 没有明确用户流程；
- 主要理由是“以后可能需要”。

## 19.4 规则文档与系统需求分离

玩法规则变化不一定要求立即开发新功能。

只要现有系统可以通过：

- 自定义属性；
- 状态效果；
- 通用对象；
- 手工变更集

表达该规则，就可以先不开发专用界面和计算器。

# 第二十三章 项目风险

## 23.1 范围膨胀

风险：

- 游戏系统不断新增；
- 每种自定义行动都要求专用功能；
- 首版迟迟无法进入测试。

控制措施：

- 使用自定义属性和状态效果；
- 优先完成完整季度闭环；
- 新玩法专用系统默认延期。

## 23.2 地图过度复杂

风险：

- 图层过多；
- 标记遮挡；
- 地图性能不足；
- 玩家难以理解。

控制措施：

- 缩放级别分层；
- 默认图层组合；
- 右侧详情面板；
- 按视口加载；
- 首版限制图层数量。

## 23.3 权限泄露

风险：

- 真实字段返回玩家；
- 搜索暴露秘密对象；
- Agent读取越权数据；
- 叙事暗示秘密。

控制措施：

- 后端玩家视图；
- 属性级权限；
- 感知投影；
- 权限自动测试；
- 主持人视角预览。

## 23.4 Agent成本和不稳定

风险：

- Token成本过高；
- 输出结构错误；
- Agent理解错误；
- 模型不可用。

控制措施：

- 单核心Agent；
- 最小上下文；
- 模型分级；
- 工具白名单；
- 主持人审核；
- 手工降级。

## 23.5 状态一致性

风险：

- 多个行动修改同一对象；
- 报告与数据不一致；
- 部分操作提交；
- 回滚不完整。

控制措施：

- 变更集；
- 世界版本；
- 事务；
- 冲突检测；
- 叙事版本；
- 快照和回滚测试。

# 第二十四章 阶段退出原则

一个开发阶段只有满足以下条件时才能结束：

1. 必须功能已经完成；
2. 核心测试通过；
3. 已知严重缺陷已经修复；
4. 权限和数据一致性没有阻塞问题；
5. 交付物已经记录；
6. 验收条件逐项确认；
7. 遗留问题已经进入技术债务或后续阶段；
8. 不再以“之后补一下”为理由忽略核心流程。

# 第二十五章 MVP最终验收场景

MVP最终验收应通过一次完整测试游戏。

## 25.1 测试流程

1. 主持人创建游戏；
2. 添加至少三名玩家；
3. 为玩家分配国家；
4. 玩家查看不同地图视角；
5. 主持人发布季度事件；
6. 玩家提交政策、外交、军事和自定义行动；
7. 玩家通过系统消息沟通；
8. 主持人截止提交；
9. 主持人整理行动；
10. 系统发现至少一个冲突；
11. 主持人创建并批准变更集；
12. 地图和国家状态更新；
13. 生成不同玩家结果；
14. 统一发布季度；
15. 开始下一季度；
16. 人为制造严重结算错误；
17. 执行季度回滚；
18. 重新结算并发布修正版。

## 25.2 通过标准

整个流程中：

- 不需要直接修改数据库；
- 不依赖Excel保存正式状态；
- 玩家不能看到越权信息；
- 所有修改可追踪；
- 回滚后旧结果明确失效；
- 系统在AI不可用时仍可完成流程。

# 第二十六章 核心结论

SrilankaOL的MVP应优先完成一个可靠的游戏运行闭环，而不是优先完成所有玩法自动化。

首版开发主线为：

> 建立游戏
> → 展示世界
> → 隔离玩家信息
> → 接收行动和消息
> → 主持人审核
> → 生成状态变更
> → 提交世界版本
> → 发布季度结果
> → 保存历史并支持回滚

世界管理 Agent、战斗模拟器和内容生成工具都建立在该闭环之上。

因此，开发顺序必须坚持：

1. 先建立世界和玩家身份；
2. 再实现地图和对象；
3. 再建立权限与玩家视图；
4. 再完成行动与通信；
5. 再完成状态变更和版本；
6. 再完成完整季度结算；
7. 最后接入AI和高级自动化。

任何不能明显帮助完成这一闭环的功能，默认不进入MVP。
